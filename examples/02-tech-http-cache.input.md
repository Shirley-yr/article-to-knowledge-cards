# 浏览器 HTTP 缓存：强缓存与协商缓存

前端性能清单里排在第一位的事情，往往不是压缩代码，而是让浏览器别重复下载。搞懂 HTTP 缓存的两层机制，能省下搜索引擎里那些含糊的"加个 cache 头"的说法。

**第一层：强缓存。** 如果响应头要求强缓存且尚未过期，浏览器直接使用本地副本，根本不发请求。你在 DevTools 的 Network 面板会看到该条目的 Size 列显示 "from disk cache" 或 "from memory cache"，状态码仍是 200。它省掉的是整个往返，收益最大。

控制强缓存寿命的是 `Cache-Control: max-age=<秒>`。它和更老的 `Expires` 头都表达过期时间，但两者同时存在时 `Cache-Control` 优先，因为 `Expires` 用的是绝对时间，受客户端时钟和时区影响。

`max-age` 的几个变体容易混：`no-cache` 不是"不缓存"，而是"允许缓存，但每次都必须向服务器确认"；`no-store` 才是真正不缓存；`immutable` 表示在有效期内连重新验证都不必做，适合带内容指纹的文件名。

**第二层：协商缓存。** 强缓存过期后，浏览器不会直接重新下载，而是带着验证信息问服务器"这个还新鲜吗"。常用的两组验证信息是 `ETag` / `If-None-Match` 和 `Last-Modified` / `If-Modified-Since`。前者用内容生成的标识符比对，精度高；后者用修改时间比对，只有秒级精度——同一秒内改了两次文件，或者文件被重新生成但内容没变，它都会判断失误。所以现代服务端优先依赖 `ETag`。

如果服务器判断内容没变，返回 304 Not Modified。304 响应只有响应头，没有响应体，因此省下的是带宽和下载时间，但一次往返仍然要付。这也是为什么"带指纹文件名 + 一年期强缓存"是最划算的组合：文件名随内容变化，内容一变 URL 就变，浏览器永远命中强缓存，一次往返都省了。

最后是操作层面的差别，它常被误当成 bug：在地址栏输入网址或点击页面内链接，浏览器会正常使用缓存；而按 Ctrl+F5 强制刷新时，浏览器会跳过强缓存、重新验证所有资源；在 DevTools 里勾选 "Disable cache" 则是在调试期间彻底绕过缓存。所以"我明明改了代码，页面却没变"多半是缓存按设计工作，而不是缓存坏了。
