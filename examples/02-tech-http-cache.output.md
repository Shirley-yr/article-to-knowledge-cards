## 卡片 1：强缓存机制

**核心知识**：强缓存命中时浏览器直接使用本地副本、根本不发请求，省掉整个往返，是所有缓存手段里收益最大的一层。

**简明解释**：当响应头要求强缓存且缓存尚未过期，浏览器连网络请求都不发出，直接在本地读取。在 DevTools 的 Network 面板里，该条目状态码仍是 200，但 Size 列显示 "from disk cache" 或 "from memory cache"，以此和真实网络响应区分。因为它跳过了请求和下载两端，所以比任何需要往返的缓存都更省。

**例子 / 自测**：在 DevTools 的 Network 面板里，某条资源的状态码是 200、Size 列却显示 "from disk cache"——此时浏览器到底有没有发出网络请求？

## 卡片 2：Cache-Control 优先于 Expires

**核心知识**：当响应同时带 Cache-Control 和 Expires 时，Cache-Control 优先生效。

**简明解释**：两者都用来表达强缓存的过期时间，但 Expires 用的是绝对时间（具体日期时刻），会受客户端本地时钟和时区偏差影响。Cache-Control 的 max-age 用相对秒数，不受时钟问题干扰，所以规范上让前者覆盖后者。配置时以 Cache-Control 为准即可。

**例子 / 自测**：同一响应里 Cache-Control 和 Expires 对过期时间的说法不一致，浏览器听谁的？

## 卡片 3：no-cache/no-store/immutable

**核心知识**：no-cache 不是不缓存而是每次都要向服务器确认，no-store 才是真正不缓存，immutable 表示有效期内连重新验证都省略。

**简明解释**：三者都写在 max-age 所在的强缓存指令里，却常被混为一谈。no-cache 允许把响应存入本地，但后续每次使用都得带上验证信息去问服务器是否仍有效；no-store 禁止任何存储，最严格；immutable 用于文件名已带内容指纹、内容确定不变的文件，在有效期内浏览器连重新验证这一步都省掉。区分它们的关键是"存不存"和"要不要再确认"。

**例子 / 自测**：想让带哈希文件名的静态资源在一年内连验证请求都不发，该用哪一个指令？

## 卡片 4：协商缓存机制

**核心知识**：强缓存过期后浏览器不直接重新下载，而是带上验证信息问服务器"这份还新鲜吗"，由服务器决定是否真正重传。

**简明解释**：协商缓存是第二层防线：本地副本过期时，浏览器不会盲目重新拉取整份资源，而是把之前记录的指纹或时间作为验证信息随请求发出，交由服务端比对。若资源没变，服务器回 304 让浏览器继续用旧的；若变了才回新内容。它省的是下载体积，但一次往返仍在所难免。

**例子 / 自测**：强缓存已经过期，浏览器下一步是直接重新下载文件，还是先向服务器确认？

## 卡片 5：ETag 内容验证

**核心知识**：ETag 由服务器根据内容生成标识符，浏览器以 If-None-Match 回传，用内容比对判断资源是否变化，精度高。

**简明解释**：ETag 把文件的实质内容映射成一个标识串，只要内容不变标识就不变。协商时浏览器把上次拿到的 ETag 放进 If-None-Match 发给服务器，服务端比较标识即可判定。由于比对的是内容本身，它能识别出"文件被重新生成但内容没变"这类时间看不出的变化，因此现代服务端优先依赖 ETag。

**例子 / 自测**：同一文件被重新生成但字节内容完全没变，用哪种验证方式能正确判定"无需重新下载"？

## 卡片 6：Last-Modified 时间验证

**核心知识**：Last-Modified 以文件修改时间做验证，精度只有秒级，同一秒内多次改动或内容未变地重生成都会让它判断失误。

**简明解释**：浏览器把服务器给的 Last-Modified 时间存下，下次用 If-Modified-Since 回传，由服务器比较时间。但它的粒度只到秒，无法区分一秒内的两次修改；文件被重新生成但内容未变时，修改时间却会变，于是它也会误判为"已变"。正因为这个局限，它通常作为 ETag 之外的补充，而非首选。

**例子 / 自测**：为什么文件在一秒内改了两次，用修改时间验证的协商缓存可能给出错误结论？

## 卡片 7：304 Not Modified 响应

**核心知识**：服务器判定资源未变时返回 304，它只有响应头没有响应体，省下的是带宽和下载时间而非往返。

**简明解释**：协商缓存里若服务器比对后发现内容没变，就回 304 Not Modified 而不重发文件主体，浏览器于是沿用本地副本。由于响应体被省掉，传输量大幅下降；但因为浏览器本就要发一次请求去确认，这一去一回的网络往返依然要付。这也正是强缓存比协商缓存更优的原因——连往返都免了。

**例子 / 自测**：一个返回 304 的响应，到底省下了什么、又没省下什么？

## 卡片 8：刷新行为的缓存差异

**核心知识**：正常浏览用缓存、Ctrl+F5 强制刷新跳过强缓存重新验证所有资源、DevTools 勾选 Disable cache 则调试期间彻底绕过缓存，三者常被误当 bug。

**简明解释**：在地址栏输入网址或点击页内链接时，浏览器照常走缓存逻辑；按 Ctrl+F5 会主动跳过强缓存、对全部资源重新验证；开发时在 DevTools 勾选 "Disable cache"，则是在调试阶段完全不读缓存。所以"我改了代码页面却没变"多半是缓存按设计工作，而不是缓存坏了——这是行为差异，不是故障。

**例子 / 自测**：改完前端代码刷新页面却看不到变化，先该怀疑缓存坏了，还是先弄清自己用的是哪种刷新方式？
